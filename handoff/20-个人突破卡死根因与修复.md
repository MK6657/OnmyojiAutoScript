> **成功到达结界突破界面**；然后就不动了：界面显示「运行中」，**日志冻结在
> `[0.8s]Page arrived page_realm_raid` 之后再无一行**（297/297 不再增长）。
>
> 用户明确：这是二开项目，自己修，留档即可。

日期：2026-07-27（用户机时区）· 涉及文件：`tasks/RealmRaid/script_task.py`（上游代码，见第 5 节 pull 提醒）。

## 1. 根因：一类「无日志 + 无超时」的 while 1 死循环

`run_2()` 到达 `page_realm_raid` 之后的执行顺序是：

```
ui_goto(page_realm_raid)        ← 日志最后一行就停在这
  ↓ screenshot + 呱太弹窗判断   （不出现就不打日志）
  ↓ ensure_lock(lock_team_enable)   ← ★ 卡死在这里
  ↓ is_frog()
  ↓ 主循环 while 1
```

`ensure_lock()` 原实现（两个分支都一样）：

```python
while 1:
    self.screenshot()
    if self.appear_then_click(self.I_LOCK, interval=1):   continue
    if self.appear_then_click(self.I_LOCK_2, interval=1): continue
    if self.appear(self.I_UNLOCK_2, threshold=0.9):       break
    if self.appear(self.I_UNLOCK, threshold=0.9):         break
logger.info(...)      # ← 只有跳出循环后才打日志
```

**只要「锁定」和「未锁定」两个图标都识别不到，这个 while 就永远出不去，而且循环体内一行日志都没有。**
对用户的表现就是：任务显示运行中、日志彻底冻住、CPU 空转截图。

为什么识别不到（任一即可触发）：

- 图标 ROI 写死在 `assets.py`：`I_LOCK/I_UNLOCK = (818,579,±38,±42)`、`I_LOCK_2/I_UNLOCK_2 = (1002,64x,~32,~40)`，
  游戏版本改版 / 活动 UI（呱太、结界突破改版）会把这个小锁挪位置或遮住；
- `I_UNLOCK_2 / I_LOCK_2` 的匹配阈值是 **0.9**，偏严；
- 分辨率或渲染差异（本机是 1280x720 + MuMu nemu_ipc）。

**同一类隐患还有 3 处**（都会静默卡死）：

| 位置 | 问题 |
|---|---|
| `base_task.wait_until_appear(target)` **不传 `wait_time` 时是 `while 1` 无限等待** | 本文件有 5 处这样调用（`I_BACK_RED` x4、`I_FIRE` x1） |
| `fire()` 的 `if retry_clean > 20: logger.warning(...)` | **只打警告不退出**，等于永远重试 |
| `check_refresh()` 的两个 `while 1` | 点了刷新等不到确认弹窗 / 弹窗关不掉就卡死 |

## 2. 修复（已应用，`python -m py_compile` 通过）

原则：**把「静默死循环」一律改成「有超时 + 有日志 + 能降级」**，不改动业务判断本身。

| # | 改动 | 行为 |
|---|---|---|
| 1 | `from module.exception import TaskEnd, GameStuckError` | 引入可被 OAS 异常处理接住的异常 |
| 2 | **`ensure_lock(..., timeout=12)`** | 限时轮询；识别到锁/未锁立即 `return True` 并打日志；**超时打 warning 并跳过锁定这一步继续跑**（锁定状态不对 ≪ 整个任务卡死） |
| 3 | `wait_until_appear(self.I_BACK_RED, **wait_time=15**)` × 4<br>`wait_until_appear(self.I_FIRE, **wait_time=15**)` × 1 | 超时返回 False 并由框架打出 `Wait until appear ... timeout`，不再无限等 |
| 4 | `fire()` 重试上限 | `retry_clean > 20` 时 `logger.critical` + **`raise GameStuckError`**，交给 OAS 自身的异常处理（保存截图 / 重启流程），不再无限重试 |
| 5 | `check_refresh()` 两个循环 | 各加 15s 上限：等不到确认弹窗→按“刷新失败”返回 False；弹窗不消失→按“已刷新”返回 True，都带 warning |

差异存档：`handoff/patches/realmraid-stuck-fix.diff`（172 行）。

## 3. 修好之后会看到什么

再跑个人突破时，日志**不会再在到达界面后凭空断掉**，而是必然出现下列之一：

- `Ensure team unlock (timeout 12s)` → `Team unlocked (...)` —— 正常继续打；
- `Ensure team unlock timeout after 12s: 识别不到锁定/未锁定图标，跳过这一步继续执行本任务` ——
  **说明就是锁图标识别不到**，任务会继续往下走（去找可打的目标）；
- 若继续卡在找目标，会看到 `No one can attack and then refresh` 之类的明确日志。

也就是说：**这次修复把"看不见的卡死"变成了"看得见的原因"**，后面无论还差什么，都能从日志直接定位。

## 3.5 验证结果（2026-07-27 05:54 实测，已确认修复生效）

   **原代码就是在这里静默死循环**；

## 4. 如果超时日志真的出现了（下一步怎么修）

说明锁图标模板对不上当前版本，属于「识别资源」问题，两条路：

1. **调阈值**：把 `assets.py` 里 `I_LOCK_2 / I_UNLOCK_2` 的 `threshold` 从 `0.9` 降到 `0.8`；
2. **重截模板**：用 `dev_tools/` 里的截图工具，在当前游戏界面重新截取锁 / 未锁图标，
   替换 `tasks/RealmRaid/res/res_lock*.png`、`res_unlock*.png`，并更新 `assets.py` 里的 ROI 坐标。

由于「锁定队伍」在当前配置里是**关闭**的（`lock_team_enable=False`），跳过这步基本无副作用。
