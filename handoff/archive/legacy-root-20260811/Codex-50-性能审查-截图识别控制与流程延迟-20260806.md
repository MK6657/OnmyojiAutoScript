# Codex-50 性能审查：截图、识别、控制与流程延迟

日期：2026-08-06
分支：`codex/mk6657-secondary-development`
账号/设备证据：`oas1` / MuMu `2301` / `1280x720`
审查方式：主代理代码与日志核验，四个只读子代理分链路审查
状态：仅审查和记录，本轮未修改业务代码

## 结论摘要

当前可感知的“慢”主要不是单一截图后端或电脑性能问题，而是多层等待叠加：

```text
截图节流
  -> 同一帧重复 OCR
  -> 状态未确认时固定等待/重试
  -> 结算、绿标、退出各自继续等待
  -> 再进入下一轮截图和识别
```

在 2026-08-06 12:39-12:45 的困28实机日志中：

- `E_AUTO_CHALLENGE` 约 601 次，单次通常约 0.12 秒；
- `BATTLE_RESULT_CONTINUE` 约 818 次；
- `BATTLE_PREPARE` 和 `BATTLE_PREPARE_WIDE` 各约 328 次；
- 结算/准备相关 OCR 的累计耗时约 70 秒以上；
- 单次绿标等待可能额外消耗 7-10 秒；
- 结算页首轮点击后存在最多约 5 秒的确认窗口；
- 探索退出确认完成后，仍可能额外等待约 5 秒的返回按钮稳定。

因此，第一阶段不应先把所有截图间隔调到最低，也不应直接把所有控制方式替换为另一种。应先消除重复识别和已知终态下的无效等待，再测量通道切换收益。

## 操作方式审查

当前账号配置为：

```text
screenshot_method = nemu_ipc
control_method = minitouch
screenshot_interval = 0.3
combat_screenshot_interval = 1.0
```

### 截图方式

`nemu_ipc` 是当前 MuMu 设备最值得保留的主路径。它直接从模拟器 IPC 取得图像，适合固定的 `1280x720` 游戏画面。

已确认的问题：

- [screenshot.py:167](D:/OSAyys/module/device/screenshot.py:167) 的 Nemu 特殊间隔分支读取 `self.config.Emulator_ScreenshotMethod`；当前真实配置字段是 `self.config.script.device.screenshot_method`。`Config.__getattr__` 对不存在字段返回 `None`，所以该分支通常静默不生效，日志仍显示 `0.3s`。
- [screenshot.py:51](D:/OSAyys/module/device/screenshot.py:51) 每次截图先经过全局节流；当前运行日志确认入口间隔约为 `0.3s`。
- [nemu_ipc.py:358](D:/OSAyys/module/device/method/nemu_ipc.py:358) 每帧先调用 `get_resolution()`，然后才采集像素；分辨率稳定时这次 RPC 可以缓存。
- [nemu_ipc.py:508](D:/OSAyys/module/device/method/nemu_ipc.py:508) 对每帧执行 BGRA 到 BGR、垂直翻转、BGR 到 RGB，存在全帧转换成本，需用哨兵图验证后再合并。

其他截图方式的定位：

- `ADB`/`ADB_nc`：适合低频页面操作或故障兜底，不适合高频战斗识别。
- `uiautomator2`：适合需要 UI 层语义的页面，不建议作为游戏画布的主截图路径。
- `window_background`：理论上可能很快，但必须验证最终分辨率；历史 benchmark 曾选出速度很快但输出非 `1280x720` 的结果。
- `scrcpy`：视频流持续接收，截图间隔控制意义不同，不应与 Nemu 直接比较。
- Web annotator 的 JPEG 编码/锁/复制只影响预览或标注链路，不是当前 OAS 核心运行链路的第一优先级。

### 点击与滑动方式

点击审查结论：

- [minitouch.py:491](D:/OSAyys/module/device/method/minitouch.py:491) 及相关路径每次点击存在约 `50ms` 的固定节拍；滑动还包含 down/move/up 多次发送和额外等待。
- ADB 点击每次有完整 shell 往返，并存在约 `50ms` 的最低节拍，不适合战斗热路径。
- uiautomator2 普通点击没有同样的固定项目级等待，但拖动包含 RPC、路径和抖动等待，适合页面语义操作，不适合高频战斗点击。
- `window_message` 普通点击默认按住约 `100-200ms`；虽然存在更快的独立路径，但没有接入标准分派，不能直接全局切换。
- 公共点击封装还会执行随机坐标、重复点击保护、历史扫描和同步日志。正常成本不是主要瓶颈，但异常重试会产生秒级长尾。

建议的通道分工：

| 场景 | 当前建议 | 原因 |
| --- | --- | --- |
| 战斗内点击、绿标、准备 | `minitouch` | 延迟稳定，已有实机链路 |
| 普通页面按钮 | `minitouch`，必要时 `uiautomator2` | 先保持行为一致，页面语义操作再单独验证 |
| 低频兜底 | ADB | 可靠性优先，允许牺牲速度 |
| 本地窗口快速点击实验 | `window_message` 独立实验 | 需验证按压时长、丢事件和窗口句柄稳定性 |
| 滑动 | 页面专用滑动实现 | 不要把战斗点击通道直接套到滑动 |

## 已确认的高收益瓶颈

### P0：已出现终态后仍继续等待绿标

位置：[general_battle.py:817](D:/OSAyys/tasks/Component/GeneralBattle/general_battle.py:817)

当前绿标逻辑最多等待 10 秒确认真实战斗；实机日志显示结算提示已经出现时，绿标等待仍可能继续。快速战斗每场可浪费约 7-10 秒。

建议：绿标等待期间一旦检测到结算/继续提示、战斗结果或任务终态，立即放弃绿标确认并交给结算流程；10 秒只保留为未出现任何终态时的上限。

### P0：结算页重复 OCR 和固定 5 秒确认窗口

位置：[general_battle.py:601](D:/OSAyys/tasks/Component/GeneralBattle/general_battle.py:601)、[general_battle.py:677](D:/OSAyys/tasks/Component/GeneralBattle/general_battle.py:677)

当前流程点击结算继续后，最多等待 5 秒，期间每轮截图并重复判断；首轮点击失败后还会进入中心坐标兜底。实机日志中一次快速结算从首次点击到完成约 7 秒以上。

建议：

- 点击后用短窗口快速确认页面是否已消失；
- 只有动画仍在变化或状态不明确时，才进入较长 fallback；
- 对同一帧复用首次结算 OCR，不要 `ocr_single` 失败后立即再次完整 OCR；
- 保留最大点击次数和超时保护，不能为了速度取消安全边界。

### P0：同一帧重复 OCR

位置：[general_battle.py:1599](D:/OSAyys/tasks/Component/GeneralBattle/general_battle.py:1599)、[general_battle.py:686](D:/OSAyys/tasks/Component/GeneralBattle/general_battle.py:686)、[Exploration/base.py:85](D:/OSAyys/tasks/Exploration/base.py:85)

已确认的重复模式：

- 准备按钮先做窄 ROI OCR，再做宽 ROI OCR；当前两者在同一帧都会执行；
- 结算页先做 `ocr_single`，失败后又调用完整 `ocr_appear`；
- 困28自动挑战按钮 `ocr_appear` 失败后又直接对同一图像调用 `.ocr(image)`；
- 退出确认模板失配时，每次轮询都重复 Full OCR。

建议引入“截图帧编号 + 识别结果缓存”，缓存范围限制在当前帧或当前状态循环内，避免把动画状态缓存过久。宽 ROI、Full OCR 和视觉兜底都应是前一步失败后的后备路径，而不是同帧并行必做步骤。

### P1：探索退出后无条件等待稳定

位置：[Exploration/base.py:270](D:/OSAyys/tasks/Exploration/base.py:270)、[tasks/base_task.py:362](D:/OSAyys/tasks/base_task.py:362)

`quit_explore()` 已经确认章节页或世界页退出成功后，`post_process()` 仍无条件执行 `wait_until_stable(UI_UI_BACK_RED)`。历史日志中退出确认后约 5 秒才出现稳定等待超时。

建议把退出端点带入后处理：已确认 `chapter_page/world` 时直接进入页面收尾；只有仍检测到返回按钮或页面过渡未完成时才做短稳定等待。

### P1：截图节拍与 Nemu 分辨率查询

位置：[screenshot.py:167](D:/OSAyys/module/device/screenshot.py:167)、[nemu_ipc.py:358](D:/OSAyys/module/device/method/nemu_ipc.py:358)

当前日志明确显示截图间隔为 `0.3s`。Nemu 特殊间隔分支因字段名不一致没有生效；同时每帧重复获取稳定分辨率。

## 建议实施顺序

### 阶段 0：先加测量，不改行为

- 记录 `SCREENSHOT_CAPTURE`、`OCR`、`MATCH`、`CONTROL_SEND`、`WAIT_REASON` 的耗时和状态；
- 为每次截图生成 frame id，统计 OCR cache hit/miss；
- 输出 P50/P95，而不是只看单次最快值；
- 用同一台 `2301`、同一分辨率和同一队伍做 A/B，避免把换阵容或网络差异当成优化效果。

### 阶段 1：低风险高收益

- 绿标检测到结算/终态时立即短路；
- 结算页首轮点击后缩短正常确认窗口，异常才进入 5 秒 fallback；
- 同一帧 OCR 缓存，宽 ROI 和 Full OCR 改为后备；
- 退出端点已确认时跳过无意义稳定等待；
- 候补页入口点击后立即确认页面状态。

### 阶段 2：截图链路

- 修正 Nemu 截图方法字段读取；
- 缓存稳定分辨率；
- 重新设计 screenshot benchmark，校验最终 `1280x720`、方向和颜色格式，使用中位数/P95；
- 在实机回归通过后测试 `0.2s`，再决定是否到 `0.15s`。

### 阶段 3：探索识别

- 给 `search_up_fight` 增加局部耗时；
- 缩小 SIFT/FLANN ROI 或改用稳定模板；
- 对地图未变化帧复用目标搜索结果，但页面变化、滑动和战斗返回必须使缓存失效。

### 阶段 4：控制通道实验

- 保持 `minitouch` 为默认；
- 用 mock 和实机分别测量 minitouch、ADB、uiautomator2、window_message 的点击/滑动 P50/P95；
- 只把实测安全的快路径接入指定页面，不做全局替换；
- 每次通道实验都验证点击是否丢失、是否重复触发、是否改变坐标方向。

## 暂不建议的做法

- 不直接把全局截图间隔改成 `0.1s`；会增加 OCR/CPU 压力，且可能放大重复识别问题。
- 不把所有点击切到 `window_message`；普通路径有更长按压等待，快路径也需要实机验证。
- 不关闭错误截图取证；当前缓存长度为 1，收益很小但会损失故障现场。
- 不先重构整个设备层；先做帧缓存、状态短路和测量，避免影响既有坐标和任务流程。

## 审查结论

性能优化应沿“减少无效工作”推进：

```text
终态短路 > 同帧 OCR 复用 > 截图节拍修正 > Nemu 采集优化 > 控制通道 A/B
```

其中前三项最可能直接改善用户感知，且不会改变核心坐标逻辑；控制方式替换放到最后，因为它同时影响点击可靠性、窗口绑定和不同任务的兼容性。
