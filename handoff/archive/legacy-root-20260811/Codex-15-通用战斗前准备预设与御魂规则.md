# Codex-15 通用战斗前准备：预设队伍与御魂规则

审查日期：2026-08-04  
分支：`codex/mk6657-secondary-development`  
性质：二次开发分支的只读审查、行为记录和后续设计基线；本轮不修改业务代码、不修改账号配置、不启动真实任务。

## 1. 本轮结论

用户确认的目标是正确的：式神录中的“预设队伍”和“换御魂”都属于战斗开始前的通用准备能力。任务可以从庭院主界面开始，也可以已经进入探索、副本或战斗准备界面后，再通过当前场景能到达的式神录入口完成准备。

两项能力必须拆开处理：

1. 阵容未锁定时，允许切换预设队伍；切换完成后，后续真实战斗应使用新的式神阵容。
2. 如果任务明确要求同时切换预设队伍和御魂，而当前阵容已锁定，应先临时解除锁定，再通过对应入口应用预设；首场战斗完成返回准备页后再尝试锁定。
3. 如果任务只要求换御魂，阵容可以继续保持锁定；锁定只阻止队伍变更，不等于禁止御魂应用。
4. 组名和队伍名是两个独立维度。队伍可能很多并且需要上下滑动；不能只按固定位置选择。目标名称在对应列表中出现重复时，应停止并提示用户重命名。
5. 任何入口都必须回到原任务所需的战斗准备上下文，再进入正式战斗。不同任务不能各自维护一套互相覆盖的准备流程。

这里的“已应用”指真实游戏状态已改变，不能只依据按钮被点击、确认框消失或某个短暂提示判断。

### 1.1 用户补充确认：右侧“使用预设”是复合动作

本轮截图确认，预设队伍行右侧的“御魂使用预设”按钮是游戏提供的统一应用入口。逻辑上要把队伍结果和御魂结果分开记录，但不能把它误解为两个必须分开点击的 UI 动作。

| 当前阵容状态 | 点击右侧“使用预设”后的队伍结果 | 点击后的御魂结果 | 处理方式 |
|---|---|---|---|
| 未锁定，当前队伍与目标不同 | 应用目标预设队伍 | 为目标队伍成员安装预设御魂 | 出现确认弹窗后点击“确定”，等待应用完成 |
| 未锁定，当前队伍与目标相同 | 队伍实质不变 | 为当前全队安装目标预设御魂 | 与直接换御魂的结果等价，同样确认弹窗 |
| 已锁定，任务只要求换御魂且当前队伍与目标不同 | 不改变当前队伍，锁定优先级生效 | 仍为当前全队安装目标预设御魂 | 保持锁定；确认后只验证御魂结果 |
| 已锁定，任务要求换队伍和御魂 | 先解除锁定，再应用目标预设队伍 | 为目标队伍安装预设御魂 | 首场战斗完成后再尝试锁定 |
| 已锁定，当前队伍与目标相同 | 队伍不变 | 仍可重新应用目标预设御魂 | 与上行相同 |

因此，统一接口应表达“选择目标预设并应用”这一意图，再根据任务是否要求换队伍和实时锁定状态决定动作：未锁定时可完成“队伍 + 御魂”，锁定且只换御魂时完成“仅御魂”，锁定但要求换队伍时先解锁再完成“队伍 + 御魂”。如果当前队伍本来就和目标一致，最终状态也与“直接换御魂”一致，不能因为队伍没有视觉变化就判定应用失败。

截图中的“即将为全队式神更换预设御魂”确认框属于正常流程，点击“确定”不是异常分支；后续必须等待确认框消失和应用结果稳定，再返回战斗准备页。

### 1.2 成功证据和预设空位兜底

本轮进一步确认了“使用预设”的两种正常成功表现：

1. 如果全队已经装备了与目标预设相同的御魂和阴阳术，游戏直接出现“全队正在使用预设御魂和阴阳术”提示。看到该提示即可判定本次应用完成，不需要再点击确认。
2. 如果当前御魂与目标预设不同，游戏出现“即将为全队式神更换预设御魂”确认框。只点击一次“确定”，确认界面消失即视为应用完成；不能要求必须再出现另一个“成功”提示。

这两个结果都属于 `APPLIED`，只是前者是“已经是目标状态”，后者是“执行了实际更换”。

用户确认的空位规则：标准战斗通常需要 5 个式神和 1 个必选阴阳师。如果目标预设只配置了 3 个式神，剩余 2 个式神位置应使用“素材”补齐。素材是兜底位，不参与核心战斗，避免把其他具有技能或行为的式神误放入战斗影响节奏；该规则需要在配置说明和实测记录中明确告知用户。

当前代码的相关能力并不等于该流程已经完成：

- `tasks/Component/ReplaceShikigami/replace_shikigami.py` 支持切换到 `ShikigamiClass.MATERIAL`、识别空位和选择式神，但主要被结界蹭卡/结界维护等育成场景调用。
- `tasks/Exploration/base.py` 的 `add_shiki()` 支持把候补式神稀有度选择为“素材”，但这是探索候补队伍，不是战斗预设应用后的当前队伍补位。
- `GeneralBattleAssets.I_PRESENT_LESS_THAN_5` 只用于拦截“当前队伍不足五个式神时打开预设”的场景，不能识别目标预设应用后产生的空位，也没有自动补素材。

因此，后续应把空位补素材作为统一准备服务的可配置兜底步骤：应用预设后识别当前战斗队伍空位，只填补式神位，不替换必选阴阳师；填补失败、素材不足或确认状态不稳定时，停止进入战斗并留下日志和截图。

### 1.3 用户补充确认：快捷预设与式神录预设是同源双视图

本轮截图确认，游戏提供的是同一套预设数据的两个入口：

| 入口 | 视觉形式 | 主要动作 |
|---|---|---|
| 战斗快捷预设 | 战斗准备页左下角“预设”，显示简化分类、分组和队伍列表 | 选择目标阵容后点击底部“出战”，回到准备页再点击“准备” |
| 式神录完整预设 | 式神录中的“预设”页，显示完整式神列表、分类和管理按钮 | 进入对应分类/分组，找到相同的目标队伍，再执行使用预设或御魂操作 |

两者不是两份配置，也不是两套命名规则。程序应使用同一组逻辑标识定位目标，只把入口适配和确认动作作为上下文差异：

```text
同一目标：分类/分组/队伍
  ├─ 战斗准备入口：快捷列表 -> 选择 -> 出战 -> 御魂提示 -> 准备
  └─ 式神录入口：完整预设页 -> 选择 -> 使用预设/换御魂 -> 返回任务页
```

因此，不能因为两个页面的布局不同，就为它们分别维护“第几个分组、第几个队伍”的配置；名称定位、滚动、重复名拒绝和结果记录必须共用。

## 2. 游戏行为模型

```text
战斗前准备
├─ 队伍预设
│  ├─ 未锁定：可以应用组名 + 队伍名
│  └─ 已锁定且任务要求换队伍：先临时解锁，再应用组名 + 队伍名
└─ 御魂预设
   ├─ 未锁定：可以应用
   └─ 已锁定：仍可以应用
```

推荐的统一流程是：

```text
识别当前场景
  -> 打开当前场景可用的预设/式神录入口
  -> 唯一匹配预设分组
  -> 在选定分组内唯一匹配预设队伍
  -> 按任务意图和实时锁定状态决定是否临时解锁
  -> 通过对应入口应用队伍与御魂
  -> 验证队伍结果和御魂结果
  -> 返回原战斗准备场景
  -> 点击准备并进入真实战斗
  -> 首场完成后按策略重新锁定
  -> 下一场以锁定状态或“准备”按钮兜底
```

队伍和御魂的执行结果必须分别记录。例如：

```text
team = LOCKED_SKIP
soul = APPLIED
```

这表示任务只要求换御魂时的合法结果，不是失败，也不能被压缩成一个简单的 `success/false`。如果任务要求换队伍，则预期结果应是先 `TEMP_UNLOCKED`，再 `team=APPLIED, soul=APPLIED`，并单独记录战后 `relock` 结果。

### 3.2 个人结界突破 RealmRaid

当前 `tasks/RealmRaid/script_task.py:354-385` 的顺序是：

1. 如果启用旧 `switch_soul_config`，从当前页面进入式神录并按数字切换御魂。
2. 如果启用旧名称御魂配置，再从当前页面进入式神录并按名称切换御魂。
3. 如果启用新名称队伍预设且配置未锁定，从式神录预设页提前应用队伍。
4. 返回并进入个人结界突破。
5. 到达结界突破页后再调用 `ensure_lock()`。

这条链路已经能支撑部分实测，但存在两个边界：

- 旧御魂流程和新队伍预设流程可以连续执行，配置指向不同预设时，最终结果由最后一次视觉操作决定，没有统一事务和结果对象。
- 如果配置写着锁定，队伍预设提前应用会被跳过；之后虽然仍可能执行旧御魂切换，但没有统一地把“锁定跳过队伍、继续换御魂”表达出来。

### 关于“锁定时目标队伍不同”的问题

此前提出的“御魂按当前式神还是按目标预设式神映射”不是在质疑上述成功判定，而是一个只在极端边界出现的映射问题。例子是：当前锁定队伍为 A/B/C，目标预设队伍为 X/Y/Z；锁定会阻止 X/Y/Z 替换进来，但仍允许点击同一个使用预设按钮换御魂。需要通过实机确认游戏是按当前队伍位置、当前式神名称，还是按预设记录映射御魂。

如果实际使用约束是“锁定时目标预设通常与当前队伍相同”，该问题不影响主流程，只需在后续实测中备案；如果允许两套队伍不同，则必须把映射规则作为准备服务的显式策略，不能靠点击后猜测。

### 3.5 用户补充确认：需要换队伍时先解锁，首场完成后再锁定

本轮又确认了战斗准备页内的实际操作链路。这里要区分“只换御魂”和“换预设队伍 + 御魂”：

```text
只换御魂
  -> 可以保持当前阵容锁定
  -> 使用预设并处理御魂提示
  -> 返回准备页

换预设队伍和御魂
  -> 判断当前是否锁定
  -> 已锁定时先解除锁定
  -> 点击战斗准备页左下角“预设”
  -> 选择预设分组和预设队伍
  -> 点击列表底部“出战”
  -> 处理“御魂不一致”提示
  -> 回到原战斗准备页
  -> 点击“准备”进入第一场战斗
  -> 战斗成功返回准备页后，再点击锁定阵容
```

后续战斗采用两条可恢复路径：

- 锁定成功：直接等待/进入战斗，不重复切换队伍。
- 锁定失败、网络延迟或点击未生效：重新截图确认，如果“准备”按钮仍在，就点击“准备”；不能假设锁定一定成功。

解锁动作本身也采用非阻塞兜底：

- 在限定时间内确认解锁成功：继续走“战斗快捷预设 -> 出战”，应用目标队伍和御魂。
- 在限定时间内无法确认解锁成功：不把队伍切换记为成功，改走目标预设的御魂应用路径，继续点击准备并进入战斗。后续是否接受当前队伍，以本场战斗在规定时限内的实际成功/失败为依据；正常成功时可以认为当前阵容本身可完成该任务。
- 该分支必须留下 `team=UNCONFIRMED` 或等价状态，不能因为御魂应用成功就伪造队伍已切换。

战后重新锁定失败时，记录 `relock_pending`，不阻塞下一场：下一场如果仍出现“准备”，直接点击准备继续；下一场战斗结束返回准备页后，再次尝试锁定。每次重试都要有有限超时，不能演变成无限点击锁图标。

预设页内的入口和动作也要单独记录：截图显示左下角“预设”打开分类和队伍列表，选中目标行后通过底部“出战”确认。它与式神录预设页中每行右侧的“使用预设御魂”按钮是两个不同的 UI 入口，虽然最终都服务于战斗前准备。

御魂不一致提示的处理规则：

1. 如果出现“检测到当前式神与队伍预设设置的御魂不一致”，可以勾选“7日内不再提示”，再点击“确定”。
2. 如果之前已经勾选过，后续可能不再出现弹窗，流程必须直接继续。
3. 点击确认后回到原战斗准备界面，才能点击“准备”；不能把弹窗消失前的状态当成战斗已开始。
4. 网络卡顿或勾选/确认失败时，必须以当前页面是否仍为准备页为依据恢复，不能盲目重复点击。

目标预设少于完整战斗人数的“换素材”流程本轮明确暂缓。原因是当前战斗准备页人数不足时，不能依靠战斗内预设按钮完成兜底；需要另行设计从战斗外补齐阵容的流程。

### 3.6 页面导航

`tasks/GameUi/page.py` 当前只注册了：

- 庭院 -> 式神录；
- 式神录 -> 庭院；
- 各任务主页面之间的基础路径。

战斗页 `page_battle` 仍被注释（约第 213 行），所以页面导航器无法表达“战斗准备页内进入式神录，再返回原战斗页”。这解释了为什么不同任务只能各自写旁路流程。

需要注意：`GeneralBattle._open_current_preset_page()` 的代码注释认为当前战斗页的“预设”按钮可能打开自动/手动战斗面板，而 `RealmRaid` 因此使用 `_open_records_preset_page()` 从式神录进入预设页。这个注释属于当前代码假设，不能覆盖用户在当前游戏版本中的实机观察；后续必须以截图和实测确认该按钮在不同场景的真实含义。

## 4. 已知问题与根因

### P1：准备能力没有统一入口

根因：任务分别调用 `SwitchSoul`、`GeneralBattle` 和自定义入口，页面图中没有战斗准备页节点，也没有统一的上下文恢复协议。

影响：困28、个人突破、八岐大蛇对同一件“战前准备”的行为不一致；修复其中一个任务容易覆盖另一个任务的结果。

### P1：锁定状态被当成配置条件，不是完整的实时门禁

根因：`battle_before()` 依赖 `config.lock_team_enable`，RealmRaid 还在任务流程中另行调用 `ensure_lock()`。配置状态和游戏当前锁图标可能不一致。

影响：可能出现队伍预设没生效但日志显示已处理，或者锁定后点击队伍预设却被误判为成功。目标规则要求以实际锁定状态决定队伍是否应用。

### P1：队伍与御魂结果没有分离

根因：现有通用战斗配置只把“是否锁定”与“是否切换队伍”绑定在一起；御魂仍由旧 `SwitchSoul` 旁路执行。

影响：无法稳定表达并验证 `team=LOCKED_SKIP, soul=APPLIED` 这种合法状态。

进一步的实机规则是：未锁定时一次“使用预设”同时完成队伍和御魂；锁定时同一按钮仍应完成御魂但不改变队伍。当前 `RealmRaid.run_2()` 在 `lock_team_enable=True` 时直接跳过新名称预设应用，正是这个规则在代码中的缺口。

### P1：旧名称御魂流程存在无硬超时循环

根因：`tasks/Component/SwitchSoul/switch_soul.py:41-58`、`178-270` 等流程多处使用 `while 1`，找不到 OCR 目标、页面识别失效或按钮模板过期时没有总超时。

影响：可能长时间卡住，且调度器会把任务误认为仍在运行。新名称队伍选择器已有上限，后续应统一使用同样的超时和证据模型。

### P2：旧御魂名称点击坐标不使用 OCR 行位置

根因：`ocr_appear_click_by_rule()` 取 `target.area` 的顶部 `y`，没有使用 OCR 命中行的中心位置（约第 287 行）。

影响：多行队伍列表中可能点到固定顶部或错误行，尤其是队伍列表需要滚动时风险更高。

### P2：成功判定缺少真实生效验证

根因：新队伍选择器在确认框消失且未抓到成功提示时，也会接受为 fallback 成功（约第 773-815 行）；没有校验当前队伍成员、锁图状态或下一场战斗阵容。

影响：视觉动作完成不等于游戏状态完成，锁定时的“无效点击”和“已经在使用预设”的提示尤其容易被误判。现有实现应精确识别“全队正在使用预设御魂和阴阳术”；如果出现御魂不一致确认框，则点击一次“确定”并以确认框消失作为完成证据，不应强制等待额外成功 toast。

### P2：配置存在双重来源和执行顺序依赖

根因：RealmRaid、Exploration、Orochi 等任务同时拥有 `general_battle_config` 和 `switch_soul_config`，任务可以先执行旧御魂、再执行新队伍，或在不同入口重复执行。

影响：用户很难判断哪个配置最终生效；后续应保留旧字段作为兼容适配层，但每个任务只提交一次统一准备请求。

### P1：首场解锁与战后重新锁定没有通用状态机

根因：当前通用战斗主要按 `lock_team_enable` 分支决定是否切队伍，缺少“准备前临时解锁 -> 应用预设 -> 首场战斗 -> 战后重新锁定 -> 锁定失败仍可准备”的跨战斗状态。

影响：可能因为提前锁定而无法应用目标队伍，也可能因为认为锁定已成功而跳过实际仍显示的“准备”按钮；八岐大蛇的 `check_lock()` 目前还有无总超时的 `while 1`，网络或模板失效时可能卡住。

## 5. 建议的统一接口（设计基线，暂不实施）

建议在 `tasks/Component/GeneralBattle` 下新增一个面向任务的 `BattlePreparation` 服务。任务只描述意图，不直接操作具体入口：

```text
BattlePreparationSpec
  entry_context: MAIN | TASK_PAGE | BATTLE_PREPARE
  return_context: 原任务战斗准备页
  team:
    enabled: bool
    group_name: str
    team_name: str
  soul:
    enabled: bool
    group_name: str
    team_name: str
  lock_policy: PRESERVE | REQUIRE_LOCKED | REQUIRE_UNLOCKED
```

执行约束：

1. 先识别当前场景，再选择主界面入口或任务内入口；不能假定始终从庭院开始。
2. 读取实时锁定状态。只换御魂时保留锁定；任务明确要求换队伍时，已锁定就先临时解锁，不能把锁定误当成“队伍切换成功”。
3. 队伍和御魂可以由一次“使用预设”复合动作完成，但必须分别验证结果；只换御魂不受队伍锁定影响。
4. 预设分组和队伍都使用名称唯一匹配、滑动扫描、上限和超时；旧数字配置通过 adapter 转换，不再与新流程并行点击。
5. 队伍结果和御魂结果分开验证和记录。
   但底层可以是一次“使用预设”点击：未锁定时期望得到 `team=APPLIED, soul=APPLIED`，已锁定时期望得到 `team=LOCKED_SKIP, soul=APPLIED`。
6. 完成后恢复原任务上下文；导航失败、验证失败和超时都返回结构化原因，不能只抛一个模糊的 `False`。
7. 同一任务同一准备阶段只执行一次；后续战斗复用已验证状态，除非任务明确要求重新准备。

推荐结果模型：

```text
PreparationResult
  team: APPLIED | LOCKED_SKIP | TEMP_UNLOCKED | UNCONFIRMED | DISABLED | FAILED | TIMEOUT
  soul: APPLIED | DISABLED | FAILED | TIMEOUT
  entry: MAIN | TASK_INTERNAL | BATTLE_PREPARE
  returned_to: 页面标识
  relock: APPLIED | NOT_NEEDED | FAILED | TIMEOUT
  relock_pending: bool
  evidence: 截图/识别结果/日志引用
  reason: 可读原因
```

## 9. 战斗失败归属与任务级策略（2026-08-04 用户确认）

### 9.1 已确认原则

本项目不建立一个覆盖所有任务的“战斗失败统一处理策略”。

只有确认已经进入真实战斗，并且游戏明确显示本场战斗失败时，才把结果交给当前任务自己的既有策略。不同任务、不同模式的失败动作必须单独讨论和确认，不能因为共用了 `GeneralBattle` 就自动共用 `EXIT`、`CONTINUE` 或 `REFRESH`。

以下情况不能直接当作“实际战斗失败”交给任务策略：

- 没有进入真实战斗，准备页超时或“准备”点击未确认。
- 预设队伍、御魂、解锁或重新锁定没有得到生效证据。
- 页面导航失败、返回上下文不确定、异常回到庭院/主界面。
- 已进入战斗，但没有看到明确的胜负结果，或结果弹窗消失后无法确认。
- 个人突破中主动投降。投降是卡级模式的业务动作，应计入该模式的失败/投降计数，但不是“实际战斗失败”。

### 9.2 结果分类基线

| 分类 | 判断依据 | 后续归属 | 当前要求 |
|---|---|---|---|
| `BATTLE_WIN` | 看到胜利、奖励或任务明确的成功证据 | 当前任务成功流程 | 正常继续任务 |
| `BATTLE_LOSS` | 已进入真实战斗，看到失败结果并完成结果页处理 | 当前任务的失败策略 | 不使用全局默认策略 |
| `SURRENDER` | 脚本主动点击投降/退出并确认 | 当前任务的业务计数或动作 | 不算普通战败 |
| `PREPARE_TIMEOUT` | 在限定时间内没有确认进入真实战斗 | 恢复/中断流程 | 记录并视严重程度通知 |
| `RESULT_UNKNOWN` | 进入过战斗但没有可靠胜负证据 | 恢复/中断流程 | 不调用战败策略，优先保守退出或等待人工确认 |
| `PREPARATION_UNCONFIRMED` | 队伍、御魂、解锁或重新锁定结果未确认 | 战斗准备状态机 | 记录未确认状态，不伪造成功 |
| `NAVIGATION_ERROR` | 未回到预期任务页面或异常回到主界面 | 任务恢复/调度器 | 记录页面证据并通知 |

### 9.3 当前代码事实和风险

- `tasks/Component/GeneralBattle/general_battle.py` 的 `run_general_battle()` 目前返回 `bool`；`battle_before()` 的返回值没有被统一检查，`battle_wait()` 的 `False` 也可能同时代表明确失败和结果未能可靠确认。这个布尔值只能作为兼容信号，不能直接作为未来统一失败协议。
- RealmRaid 普通模式已有 `WhenAttackFail.EXIT/CONTINUE/REFRESH` 配置；当前默认值是 `REFRESH`。普通模式应暂时保留这套任务级策略，后续只按实测确认其含义，不扩散给其他任务。
- RealmRaid 目标等级模式有独立的棋盘、checkpoint、成功数和投降数状态机。它的主动投降、实际胜负、手动刷新和自动刷新不能套用普通模式的 `WhenAttackFail`；目标等级模式的规则以已确认的卡级文档为准。
- 困28的 `tasks/Exploration/base.py::fire()` 当前调用通用战斗后没有读取返回值，仍会增加 `minions_cnt` 并返回成功。也就是说，真实战败可能被任务当成已完成的一次挑战，这是待单独确定失败策略前必须保留的已知风险。
- 八岐大蛇的多个队长/队员/野队循环调用通用战斗后没有统一检查单场返回值；当前主要由邀请失败、房间死亡、次数或时间限制控制任务结束。实际战败后的动作尚未被本项目重新确认。
- `run_general_battle()` 在战前先增加战斗计数；如果准备阶段没有真正进入战斗，计数可能已经变化。这属于“准备失败与实际战败混淆”的现有架构风险。

### 9.4 必须逐任务确认的问题

以下问题暂不自行决定，后续实测对应任务时逐项确认并追加到本节：

1. RealmRaid 普通模式是否继续完全沿用当前 `WhenAttackFail`；目标等级模式是否明确忽略该配置，仅使用卡级状态机。
2. 困28确认实际战败后，是重试同一个目标、跳过当前目标挑战下一个、结束本轮任务，还是按次数/时间继续；本场战败是否计入任务的完成次数也要明确。
3. 八岐大蛇在队长、队员、野队三种身份下实际战败后的动作是否一致；是结束当前房间、继续下一场，还是只记录失败并在时间/次数范围内继续。
4. 其他调用 `run_general_battle()` 的任务是否有自己的失败规则，哪些任务需要纳入下一轮审查。
5. “必要时通知”的触发边界：准备超时、结果不确定、异常回主界面、解锁/重新锁定持续未确认应立即通知；连续实际战败的阈值和通知方式需要按任务另定。

### 9.5 审查和实现约束

后续若实现统一结果模型，应先保留任务自己的失败策略，再把通用战斗返回值细分为 `BATTLE_WIN`、`BATTLE_LOSS`、`PREPARE_TIMEOUT`、`RESULT_UNKNOWN` 等结构化结果。未完成这一步前，不应把所有调用点的 `False` 统一改成退出、刷新或重试。

本节是规则和风险留档，不代表已经修改代码；任务级策略在用户逐项确认前保持未定。
