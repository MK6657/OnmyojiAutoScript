# 交接 21 · 「打九退四」卡在退出确认弹窗 · 根因与修复（二开）

> 现象：handoff/20 修好 `ensure_lock` 后，个人突破能正常找目标、进攻、打赢、领奖。
> 但当目标是**左上角第一个**（`index == 1`）且开启了**打九退四**时，游戏停在
> **「确认退出战斗吗？」** 弹窗上不动，日志反复刷 `Click ( xx, xx) @ GB_EXIT`，
> 随后触发游戏重启，进入「重启 → 登录 → 回结界突破 → 又卡」的循环。

日期：2026-07-27 · 涉及文件：`tasks/Component/GeneralBattle/general_battle.py`（上游代码）。

---

## 1. 根因：又是「无超时 while 1 + 模板认不出」

`run_2()` 中 `index == 1` 且 `exit_four` 开启时会调用
`run_general_battle_back(config, exit_four=True)`，而该方法原本有 **4 个没有超时的 `while 1`**：

```python
# 点击返回
while 1:
    self.screenshot()
    if self.appear_then_click(self.I_EXIT, interval=1.5):   continue
    if self.appear(self.I_EXIT_ENSURE):                     break   # ← 死等确认弹窗被识别
logger.info(...)
```

`I_EXIT` 是战斗界面**左上角**的退出键（roi `14,12,43,41`），
`I_EXIT_ENSURE` 是弹窗里的**确认**按钮（roi `674,388,135,63`，阈值 0.8）。

实际发生的是：点了退出 → 弹窗**已经弹出来了**（用户截图可见「确认退出战斗吗？」），
但 `I_EXIT_ENSURE` 的模板**匹配不上** → 循环条件永远不满足 →
不停地去点左上角退出键，而弹窗正挡在前面，点了完全没用 → 静默卡死。

**这与 handoff/20 的 `ensure_lock` 是同一个病根**：上游大量使用
「`while 1` + 图像识别 + 无超时 + 循环体内无日志」的写法，只要某个模板因
游戏改版 / 分辨率差异认不出，任务就会无声无息地卡住。

## 2. 修复

| 位置 | 改动 |
|---|---|
| `run_general_battle_back` | 4 个循环全部限时（12s）；`wait_until_appear` 补 `wait_time`；识别不到确认按钮时**按 `I_EXIT_ENSURE` 的 ROI 中心盲点一次兜底**；返回值改为 `ok`（是否完全顺利），调用方原本就忽略返回值，无副作用 |
| `exit_battle` | 同样加 12s 超时 + ROI 中心盲点兜底；确认阶段超时返回 `False` 交上层处理 |

差异存档：`handoff/patches/generalbattle-exit-fix.diff`（131 行）。`py_compile` 通过。

## 3. ★ 生效方式与 handoff/20 不同（重要）

- `tasks/RealmRaid/script_task.py` 是通过 `load_module()` → `exec_module()` **每次执行任务都从磁盘重新加载**，
  所以 handoff/20 的修复**点「停止 → 启动」就生效**。
- `tasks/Component/GeneralBattle/general_battle.py` 是被 `import` 的普通模块，
  **Python 会缓存在 `sys.modules` 里** —— 即使 `script_task.py` 重新执行，
  它的 `from ... import GeneralBattle` 仍拿到旧的类。
  **因此本次修复必须重启 OAS Core 才会加载**（关掉「OAS Core」窗口 → 双击 `启动.bat`）。

## 4. 立即止血：关闭「打九退四」

为了不等重启就能正常跑，已在界面把 **个人突破 → 打九退四(`exit_four`) 关闭并保存**。

依据：`run_2()` 里 `run_general_battle_back` **只在 `exit_four` 为真时被调用**，
关掉它就完全不会走这段坏掉的退出流程，机器人直接正常打。

**验证（2026-07-27 06:12 实测）**：关闭后重启任务，日志干净：

```

Ensure team unlock (timeout 12s) → timeout 12s 跳过（handoff/20 的修复照常生效）
[NUMBER] [10/30]
Find one medal [RES_MEDAL_0], order is 9 → Click fire 9 success
GENERAL BATTLE START → Current count: 1 → Preset is disable
```

票数持续递减、连续进攻 —— 稳定运行。

## 5. 想恢复「打九退四」怎么办

1. 关掉「OAS Core」窗口 → 双击 `启动.bat`（让本次 `general_battle.py` 的修复加载）；
2. 界面里把 **打九退四** 重新打开并保存；
3. 观察日志：
   - 若出现 `gb_exit_ensure ... 按 ROI 中心盲点一次兜底` 且随后战斗正常退出 → 兜底奏效，可以一直用；
   - 若仍退不出去 → 说明弹窗位置也变了，需要**重截模板**：
     用 `dev_tools/` 的截图工具在「确认退出战斗吗？」弹窗上重新截取确认按钮，
     替换 `tasks/Component/GeneralBattle/gb/gb_exit_ensure.png`，并按实际位置更新
     `tasks/Component/GeneralBattle/assets.py` 里 `I_EXIT_ENSURE` 的 `roi_front/roi_back`。

## 7. 顺带记录：包名不是标准包

日志中出现过：

```
App start: com.netease.onmyoji → No activities found to run → PackageNotInstalled: com.netease.onmyoji
<<< DETECT PACKAGE >>> → com.netease.onmyoji.wyzymnqsd_cps → Auto package detection found only one package, using it
```

这台机器装的是**渠道服**包 `com.netease.onmyoji.wyzymnqsd_cps`，而默认包名是 `com.netease.onmyoji`。
每次重启游戏会先失败一次再自动探测，属于可容忍的浪费；若想彻底干净，可在
「运行设置 → 游戏客户端(`package_name`)」里显式选择该渠道包（前提是下拉里有该选项）。
这一失败也可能是触发多余「自动重启」的诱因之一，值得后续观察。
