## 2. 已完成的目标选择修正

原实现把整个目标卡分区当作随机点击范围。这样会点击到空白或状态区域，点击动作本身不能证明目标详情已经打开，也会造成误判和异常重试。

当前实现按目标卡建立两个有语义的局部候选区域：首枚勋章和头像。每个候选之间等待界面稳定，并且只有检测到真实“进攻”按钮后才认定目标选择成功。名称区域已明确排除：目标卡选中后点击名称会进入玩家友人帐，不是挑战入口。专项测试验证了候选区域、最多两次尝试和失败诊断截图。

## 4. 根因

详情卡打开后，NEMU IPC 返回了 `720x1280` 的旋转原图。代码链路存在两个问题：

1. `Screenshot.screenshot()` 原本把 `_handle_orientated_image()` 注释掉，竖屏截图没有在进入模板匹配前归一化。
2. `check_screen_size()` 在第一次通过 `1280x720` 后使用 `_screen_size_checked` 短路，后续详情卡阶段的竖屏截图不会再次被处理。

最终固定 `1280x720` ROI 在 `720x1280` 原图上匹配，日志出现大量 `No usable template`，随后通用页面识别得到 `Unknown ui page`，任务按失败重调度。方向归一化后的独立截图又发现 `I_FIRE_CURRENT` 的旧搜索区只覆盖到 `y=600`，而当前居中详情弹窗的“进攻”按钮位于 `y=629`，因此该备用规则也无法覆盖真实按钮。

实机截图旋转验证表明，逆时针旋转后画面恢复正常横屏，且“进攻”按钮位于预期的横屏卡片底部。错误日志中还出现 `Device Orientation 0 (Normal)`，说明这次 MuMu 详情卡旋转没有可靠反映到 `dumpsys display`；不能只依赖该字段判断截图方向。

## 5. 本轮修复

公共截图层现在在每次截图进入页面识别前执行方向归一化：

- `1280x720` 原图直接使用。
- `720x1280` 竖屏图按当前逻辑方向旋转到 `1280x720`。
- 当竖屏图同时报告 `orientation=0` 时，采用 MuMu 当前版本验证过的逆时针回转路径，并把逻辑触控方向同步为 `1`，避免识别坐标和 minitouch 点击坐标不一致。
- 新增离线测试覆盖竖屏回转、方向同步和横屏原图不变。
- 移除 `partition_*:name` 候选，避免已选中目标进入友人帐；当前最多只尝试勋章和头像两个安全区域。
- 扩大 `I_FIRE_CURRENT` 搜索区到 `y=250..720`，覆盖当前居中详情弹窗底部的真实“进攻”按钮。
- RealmRaid 子类增加“结算提示 + 个人突破返回按钮”的专用分流，优先点击 3/6/9 奖励弹窗一次，再回到棋盘稳定检测，避免交给通用战斗结算循环误点三次。
- GeneralBattle 的结算 OCR 现在要求识别文本同时包含“屏幕”和“继续”；仅包含“点击”的战斗准备文字（例如“点击式神区域进行配置”）不再被当作结算提示。

本修复不改变 RealmRaid 的等级、胜负、投降、奖励或刷新计数逻辑，只修正截图与触控坐标的公共坐标系。

## 8. 2026-08-05 14:38 复核：友人帐与九胜奖励覆盖层

### 8.1 友人帐点击的最终定性

旧证据中的 `partition_8:name` `(711,445)` 确实进入友人帐，但它发生在目标卡已经选中后，名称区域本身就是玩家资料入口。它不是 `1280x720` 坐标整体偏移，也不是窗口缩放造成的随机漂移。当前代码已经移除 `partition_*:name` 候选，只保留首枚勋章和头像两个挑战入口。

2026-08-05 14:38 的最新一轮没有再出现友人帐点击：日志使用 `partition_3:first_medal` `(935,214)`，随后点击 `RES_FIRE` `(1050,385)` 并确认进入目标 3。该轮真正的失败点是九胜奖励覆盖层，不应再归因到友人帐或坐标偏移。

### 8.2 九胜奖励覆盖层真实证据

失败截图 `log/board/realm_raid_board.png` 显示：背景仍是个人结界突破棋盘，中央是蓝色大型奖励动画，底部有“点击屏幕继续”。程序却把它当作通用 `BATTLE_RESULT_CONTINUE`，先点击 `(615,703)`，再用中心兜底 `(629,332)` 和 `(720,674)`，三次后以 `Battle result continuation remained visible after 3 clicks` 中断并按短重试退出。

旧专用分流只依赖 `I_BACK_RED`；当前蓝色奖励动画会使旧 `I_SOUL_RAID` 模板分数降到约 `0.464`，原有暖色形状检测的暖色比例约 `0.032`，因此专用分流没有接管，最终落入通用结算循环。

### 8.3 已实施的最小修复

- 九胜奖励形状检测同时支持旧红/橙色和当前蓝色奖励对象，并要求画面明显变暗，避免普通明亮棋盘误判。
- RealmRaid 结算分流现在使用“结算提示 + 棋盘返回锚点或奖励形状”判定；返回按钮模板短暂漏检时仍可由独立奖励形状接管。
- 点击动作仍复用已有一次性奖励弹窗处理和中心兜底，不改变等级、票数、胜负、投降、刷新或调度策略。
- 新增蓝色覆盖层和“返回按钮模板缺失但形状明确”的回归测试。

离线证据：真实奖励截图的启发式结果为 `True`，正常棋盘 `manual_current_lock_state_20260804.png` 为 `False`。`unittest` 相关测试 `9/9` 通过，`compileall` 和 `git diff --check` 通过；当前环境没有安装 `pytest`，未运行 pytest 命令。
