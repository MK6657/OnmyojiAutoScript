## 根因与处理

`RealmRaid._dismiss_battle_result_continue()` 原先先判断固定 `I_SOUL_RAID`/奖励启发式。普通结算页也能命中同一ROI，导致通用“点击屏幕继续”未先处理，后续棋盘等待器把结果页当作未消失的3/6/9奖励。已改为通用结果优先，真正无通用提示时保留奖励兜底。

离线专项测试修复后为 `57/57` 通过；尚无修复后的实机成功证据，因此本事项不能结案。

## 结论

### 第二轮实机失败（02:13）

- 从 checkpoint 恢复后，棋盘识别为目标 `58`，成功 `7`、失败 `4`、票数 `29/30`，继续攻击目标 `1`。
- 点击挑战后，程序在战前预检查阶段命中 `I_SOUL_RAID` 固定奖励 ROI，点击 `(640,540)`；此时真实页面仍是战斗准备页，日志随后持续出现 `BATTLE_PREPARE=准备`，未进入战斗。
- `wait_level_board` 约20秒超时，任务以 `attack_unconfirmed` 暂停；现场截图：[after-failure.png](../../../log/Codex-2026-08-07-RR-COMBAT-001-after-failure.png)。

### 根因与修复

准备页 OCR 首帧可能为空，所以仅依赖 `is_in_prepare()` 的门禁不够。RealmRaid 的任务专属奖励兜底必须由调用上下文授权，不能在通用战前预检查阶段运行。

已实施：战前调用 `_dismiss_battle_result_continue(allow_task_reward=False)`；RealmRaid 在该标志为 `False` 时保留通用结果提示处理，但跳过 `I_SOUL_RAID` 奖励处理。战斗结果阶段仍使用默认 `True`，不改变正常3/6/9奖励流程。

离线验证：RealmRaid `80/80`、GeneralBattle `81/81`，结果专项 `16/16` 与 RealmRaid 覆盖 `7/7` 通过；尚无修复后的实机成功证据。

`RR-COMBAT-001` 仍为“待实测”，下一步只做同 checkpoint 单场复测。验收顺序为：准备页点击/进入真实战斗 -> 自动模式 -> 战斗结束 -> 结果/奖励 -> 回板 -> checkpoint 更新；任一环节异常立即停测并保留现场证据。
