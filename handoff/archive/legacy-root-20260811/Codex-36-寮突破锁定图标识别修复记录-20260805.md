# Codex-36 寮突破锁定图标识别修复记录

日期：2026-08-05  
范围：仅修复 `tasks/RyouToppa` 寮突破页面的锁定/未锁定图标识别搜索范围。

## 现象

第一版寮突破已经完成预设准备并进入正确的寮突破棋盘，但在棋盘前的阵容状态确认阶段，12 秒后以 `team_lock_state_timeout` 安全退出。运行日志为：

```text
RYOU_ENTRY_STATE board
RYOU_LOCK_STATE_TIMEOUT desired=unlocked
RyouToppa task end: success=False, reason=team_lock_state_timeout
```

这次没有进入战斗，也没有消耗突破次数或自动选择其他阴阳寮。

## 根因

`RuleImage.match()` 使用 `roi_back` 作为模板搜索窗口。原来两个模板的搜索窗口分别从 `(203,602)` 和 `(202,603)` 开始，几乎等于模板本身尺寸。

实机截图 `log/diagnostics/ryou_board_after_entry.png` 中，未锁定图标的真实模板左上角约为 `(198,603)`。因此原搜索窗口没有包含模板，匹配分数只有 `0.189`，程序未执行误点击，而是等待超时。

## 修复

锁定和未锁定图标都使用有界搜索窗口：

```text
roi_back=(190,595,48,43)
```

`roi_front` 仍保留原始标称位置；模板命中后，`RuleImage.match()` 会把实际命中位置写回 `roi_front`，后续点击使用重新定位后的图标中心。

窗口只覆盖左下角阵容控件附近，不扩展到棋盘目标区域。资源源文件 `dev/image.json` 与生成后的 `assets.py` 已同步。

## 离线证据

针对截图与未锁定模板的模板匹配结果：

| 搜索窗口 | 最高分 | 命中位置 |
| --- | ---: | --- |
| 原窗口 `(202,603,26,32)` | `0.18949` | 无效命中 |
| 修复窗口 `(190,595,48,43)` | `0.93011` | `(198,603)` |

锁定模板在当前截图中不可见，未将其误判为锁定；这是预期行为。

## 第二个实机问题

重启 Core 后再次运行，日志已经证明锁定图标修复生效：

```text
RYOU_ENTRY_STATE board
RYOU_LOCK_STATE state=unlocked
RYOU_TICKET_STATUS available
RYOU_AREA_CLICK area=1, attempt=1
```

随后页面没有进入准备/战斗状态，连续等待 20 秒后重试，最终为 `click_timeout`。对照旧版 `attack_area()` 可见，选中区域后还必须识别并点击 `RealmRaidAssets.I_FIRE`；新链路漏掉了这个寮突破专属的“进攻”确认按钮。现已在 `_wait_for_battle_entry()` 前置消费 `I_FIRE`，并兼容当前版本的 `I_FIRE_CURRENT`。

## 验证

- `tasks/RyouToppa/tests/test_ryou_flow.py` 新增回归测试，确认两个模板尺寸均被修复窗口完整覆盖。
- `tasks/RyouToppa/tests/test_ryou_flow.py` 新增回归测试，确认寮突破两个版本的进攻按钮都会在战斗状态判断前被点击。
- 已完成一次 Core 重启后的实机验证，确认锁定图标识别通过；进攻按钮补丁尚未完成第二次实机验证。
- 下一步应在用户已手动选择的目标阴阳寮页面运行一次，确认日志出现 `RYOU_ATTACK_CONFIRM variant=I_FIRE` 或 `I_FIRE_CURRENT`，随后出现 `RYOU_BATTLE_START area=1`。

## 边界与未处理项

- 本次不修改寮选择逻辑，程序仍不会自动选择第一个阴阳寮。
- 本次不修改绿标逻辑；绿标仍按既定 `green_left2` 记录观察。
- 若后续模拟器缩放造成超过约 8 像素的位移，应先保存新截图和匹配分数，再调整窗口，不直接扩大到整块棋盘。
