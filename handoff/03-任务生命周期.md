# 任务生命周期

## 层次

~~~text
Scheduler
  -> account runtime
    -> task process
      -> scene/state machine
        -> one battle
          -> result/reward/return
~~~

调度器负责决定何时拉起任务和何时延期；任务负责自己的业务流程；单场战斗负责进入、自动战斗、结果和回板。不能把单场结束误当作整项任务结束。

## 状态定义

- scheduled：等待调度器拉起。
- starting：正在建立账号、设备和任务上下文。
- running：任务实例正在执行。
- waiting：任务因冷却、资源不足或用户安排等待。
- idle：没有可执行任务，但服务仍保持运行。
- stopped：用户明确停止或实例已清理。
- failed：出现需要记录的异常。
- completed：达到当前任务明确的完成条件。

## TaskEnd 与 next_run

TaskEnd 表示任务实例本轮控制流结束；next_run 表示调度器下一次选择时间。两者必须在日志中分别记录，不能依赖“先写 next_run 再抛异常”的隐式顺序判断完成。

当前 `TaskEnd` 固定携带：

- `outcome`：`returned`、`aborted` 或其他明确终态。
- `success`：只表示本轮任务结果，不从异常类型反推。
- `reason`：人和程序均可读的结束原因。
- `statistics`：当前任务可复核的计数或失败预算。
- `next_run`：任务明确知道时记录；否则为 `None`，调度事实以 `SCHEDULE_DECISION` 为准。

项目中的业务任务不得再直接构造无字段 `TaskEnd()`。战斗层使用 `BattleOutcome` 区分 `not_started`、`active_unconfirmed`、`victory`、`defeat`、`settling`、`returned` 和 `aborted`；`GotoMain` 遇到 `page_battle` 时返回 `active_unconfirmed`，不越权点击结算/继续。

任何任务结束时至少记录：

- 任务 ID、账号 ID、实例 ID。
- 当前阶段和最后确认页面。
- TaskEnd 原因。
- 是否写入或延期 next_run。
- checkpoint、票数、计数和错误。
- 是否允许调度器继续选择下一项。

## 调度写入

调度统一经过 `Config.schedule(task, when, reason, caller)`。日志 `SCHEDULE_DECISION` 必须包含任务、目标时间、旧时间、调用者和原因。

- 正常完成使用成功间隔。
- 可恢复失败先写失败间隔，再结束本轮任务，避免旧到期时间触发立即重跑。
- 用户禁用任务时，历史 next_run 可保留为审计事实，但不表示任务正在运行。
- 跨任务调度使用显式白名单；默认只能修改当前任务。已声明的探索、斗技、活动监控、Restart、控制中心和组队同步关系才允许写其他任务，未授权调用在保存前失败。

## 恢复规则

- 未确认的页面状态不能直接标记成功。
- checkpoint 只允许对应任务恢复，不得被其他任务越权修改。
- 任务异常后先保存现场，再决定重试、延期、人工接管或退出。
- 同一账号不能同时运行困28、个人突破、寮突破等互相竞争设备的任务。
- Core 启动、停止和 reaper 共用账号生命周期锁；每轮任务使用独立 IPC 队列和管道。
- Bridge 只有收到 Core 的 `completed/failed` 最终回执后才能向前端报告结果，socket 发送成功不代表任务已执行。
