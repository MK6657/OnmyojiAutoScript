## 一、这次联调是怎么做的

13 号文档交付时，前端只对着一个轻量 mock bridge 验证过契约，真实 Bridge 代码没有真正跑起来过。
这次把三层真的接起来跑了一遍：

```text
UI-claude（浏览器，Playwright 驱动真实交互）
      ↓ HTTP + WebSocket（跨端口直连，CORS 走真实代码路径）
真实 Bridge（control-center/bridge/app，即交付的那份代码）
      ↓ HTTP + WebSocket
mock Core（bridge/tests/mock_core.py，接口逐条对齐 module/server/script_router.py）
```

mock Core 是新增的**可执行契约**：真实 Core 的每个被依赖接口（含 WebSocket 的
state/schedule/文本日志行为、`config_copy` 静默重名、value 接口的严格时间解析和
pydantic 校验失败返回 false 等"特色行为"）都在里面复刻了一份。任务字段结构从
真实 `config/*.json` 派生。它不写任何文件，仅在内存运行。

为什么不直接连真实 Core 联调：启动/停止/改配置这类用例会真实操作游戏配置，
不适合自动化反复执行；mock Core 让全部用例可以无副作用地跑，而真实 Core 的
最终验收（见第五节）仍留给真实设备。

## 二、联调发现并修复的缺陷

### F1 秒断退避在真实时序下无效（重连风暴仍在）— `bridge/app/runtime.py`

13 号文档 B6 修的"空任务账号重连风暴"，判据是「连上不到 3 秒**且没收到任何消息**」。
联调实测推翻了它：真实 Core 断开前会先推一条 `{"state":0}`，"收到过消息"每次都成立，
计数器每次都被清零。**实测数据：修复前 15 秒内重连 12 次；修复后 3 次，之后进入 30 秒退避。**

修法：判据只看存活时长——存活不足 3 秒即计一次秒断，连续 3 次退避 30 秒。
健康的空闲连接会保持在线几分钟以上，不会误伤。代码内有注释引用本文档。

### F2 保存"假成功"：Core 校验失败返回 false 被当成功 — `bridge/app/core_client.py`

真实 Core 的 `script_set_arg` 在 pydantic 校验失败（枚举值不合法、字段不存在）时
返回 `false` 且 HTTP 200。Bridge 原样吞掉：界面提示"已保存"，配置文件里什么都没写。
这是数据安全级的问题——用户以为改了御魂配置，实际没改，任务照旧跑。

修法：`set_value` 检查返回值为 `false` 时抛错，前端收到 502
「OAS Core 拒绝了 {group}.{name} 的值」。集成用例覆盖：写入非法枚举 → 502 →
穿透读回确认原值未被污染。

### F3 启动时无窗口弹打扰性警告 — UI-claude `src/App.jsx`

模拟器还没开时，界面一启动就弹「没有读到窗口列表」。改为：启动时的预取静默，
只有用户主动点「刷新窗口」才提示结果。

另：Bridge 版本号提升为 **1.1.1**（`/api/v1/health` 可见），便于确认线上跑的是修复后的构建。

集成层验证过的关键链路（摘录）：

- 账号列表首次加载 161 次 Core 请求（3 账号全量扫描），第二次 **0 次**（缓存），
  runtime 连上后 **0 次**（调度快照）——13 号 B1 的修复在真实进程里成立；
- `date_time` 16 位输入、`time_delta` "0 6:0:0" 这类不规范值，经 Bridge 规范化后
  被 Core 的**严格 strptime** 成功解析并落库——B3 修复闭环；
- 启动 → 状态经「Core WS → Bridge 事件 WS → 浏览器」变为运行中，OAS 格式日志
  实时回流且 INFO/WARNING/ERROR 级别解析正确（界面可按级别过滤）——B7 闭环；
- Core 故障（fault 开关）→ health 显示 offline、保存报可读错误；恢复后重试成功；
- 账号创建/重命名/删除在 Core 侧同步生效，重名创建 409——B8/B9 闭环；
- 模板经 Bridge SQLite 持久化，设置页显示「Bridge 数据库」存储位置。

## 五、上游（runhey/OnmyojiAutoScript）更新时怎么办

控制中心对上游的依赖面**只有** Core 的 HTTP/WS 接口，全部落在两个文件里：
`bridge/app/core_client.py`（调用方）和 `bridge/tests/mock_core.py`（契约的可执行副本）。
上游更新后按这个顺序走，一般 10 分钟内能确认兼容性：

1. **先只更新上游**（`module/`、`tasks/`、`server.py`），控制中心不动；
2. 起真实 Core，跑 `check-wiring.ps1` —— 逐层只读探测，哪层红修哪层；
3. 红了或行为可疑时，对照下面的契约清单定位：

   | 依赖点 | 上游位置 | 变化时改哪里 |
   |---|---|---|
   | `GET /test` 返回 `"success"` | script_router.py | core_client.health |
   | `GET /script_menu` 结构（dict: 分组→任务ID列表） | config_menu.gui_menu_list | bridge.catalog + main.TASK_LABELS/CATEGORY_LABELS + 前端 locale.js |
   | `GET /config_list` / `config_new_name` / `config_copy`(静默重名) / `PUT|DELETE /config` | script_router.py | core_client + main 的账号接口 |
   | `GET /{cfg}/{task}/args` 字段结构（name/title/type/value/enumEnum） | config_model.script_task | main.task_config；新类型还要加 fields.jsx 控件 |
   | `PUT .../value` 的 types 集合与时间格式（`%Y-%m-%d %H:%M:%S` 等）、校验失败返回 false | script_router + config_model.script_set_arg | core_client.normalize_value / set_value |
   | `GET /{cfg}/start|stop`（REST 兜底） | script_router.py | core_client.start_script/stop_script |
   | `WS /ws/{cfg}`：state 0/1/2/3、schedule{running,pending,waiting}、文本日志行、空任务秒断 | script_router + script_process | runtime.py（STATE_LABELS / scheduled_tasks / 日志解析 / 退避） |

4. 改完 Bridge 后**同步改 mock_core.py**（保持契约副本与上游一致），然后依次跑
   `test_bridge.py` → `start-dev-stack.ps1` + `test_integration.py` + `e2e-real.mjs`；
5. 只有中文映射缺新任务/新字段时，改前端 `locale.js` 即可，不用动 Bridge；
6. 在变更记录里补一行：上游 commit、改了哪层、跑过哪些回归。

上游新增任务/字段的**默认安全性**：任务目录来自 `/script_menu` 动态获取，新任务会
自动出现（没翻译时显示英文 ID）；新字段由通用 Schema 渲染成对应控件，匹配不上的
类型降级为文本框——不会白屏，只是暂时不够漂亮。
