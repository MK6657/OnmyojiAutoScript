## 1. 一键扫描绑定模拟器窗口（annie 式）

### 原理（为什么能做，且不用动 Core）
- OAS 的设备配置 `script.device` **本来就有 `handle` 字段**（真实 `config/oas1.json` 里 `"handle": ""`），
  就是「绑定到某个窗口句柄」——annie 也是绑 `MuMuNxDevice.exe` 的窗口句柄，同一套路。
- Bridge 的 `GET /api/v1/windows`（`visible_windows()` 用 Win32 `EnumWindows`）已经能扫出每个可见窗口的
  `handle / title / pid / process`。能力早就通了，只是原来埋在「运行设置 → 设备 → handle」的下拉里，用户找不到。

### 做了什么
- 新增显眼入口：**概览「设备」检查行的「🔗 扫描并绑定窗口」** + **顶部账号名旁的「绑定窗口」**。
- 点开弹窗 `WindowBindDialog`：扫 `/windows` → **按进程名/标题过滤出模拟器窗口**（MuMu/雷电/夜神/蓝叠/逍遥，
  见 `src/emulator.js`），每行显示 `标题 · 类型标签 · 进程 · 句柄`；识别不到就退回列全部窗口。
- 选中一个窗口 → `bindWindow()`：
  1. 读该账号 `Script` 配置，拿 `device.handle` / `device.emulatorinfo_type` 的真实字段类型与枚举选项；
  2. 组装 `handle = 窗口句柄`（一定写）+ `emulatorinfo_type = 识别值`（**仅当它是 Core 真实枚举里的合法项才写**，
     否则保持 auto，绝不写非法值被 Core 拒）；
  3. `PATCH .../Script/config` 保存 → 重读配置刷新「设备已绑定」。
- 全程只用 `GET /windows` + `GET/PATCH /Script/config`，**不改任何 Core 代码**。

### 关键修正：区分「显式绑定」与「自动检测」
- 原来 `serial=auto` 被 `deviceSummary` 判为「已绑定（设备：自动检测）」，检查是绿的——但 auto 只是「让 Core 自己找」，
  多开/环境不对时常连不上，用户就卡在这（**正是他的原始问题**）。
- 现在 `deviceSummary` 增加 `explicit` 标记：只有绑了 `handle` / 非 auto 的 `serial` / 具名模拟器才算 `explicit`。
  auto 状态仍算「可启动」（不硬拦），但概览那行会提示「未手动绑定窗口，连不上就点右侧绑定」，并把绑定入口露出来。

### 现实提醒（写给维护者，不是 bug）
`handle` 是 OAS 支持的窗口绑定方式；若某些机器上仅绑 handle 仍连不上，多半还需要 `serial`（ADB，如 MuMu12 常见
`127.0.0.1:16384`）。窗口扫描拿不到 ADB 端口，所以本功能不臆测 serial（保持 auto）。需要时在「运行设置 → 设备」手填 serial。

## 2. 任务开关乐观更新（修「发木/没反应」）

- 原来点开关要等真实 Core 一个来回（OCR/ADB 可能 1~3 秒）开关才动，显得没反应。
- 改为**乐观更新**：点击即时翻转开关和「N 项任务」计数；后台再 `setTaskEnabled` + 对账，写失败回滚到服务器真实状态。
- 附带：点任务名读配置时，右侧从「选择一个任务」改为**「正在读取配置…」**，避免慢 Core 下以为没反应。

## 5. 日常怎么用（给用户）

1. 打开模拟器和游戏 → 概览点「🔗 扫描并绑定窗口」→ 选中你的窗口（如 `2301 / MuMuNxDevice.exe`）→ 自动保存；
2. 「任务」页用右侧开关启用要跑的任务；
3. 回概览过启动前检查 → 启动 → 去「日志」看。
   若绑定后仍连不上，到「运行设置 → 设备」把 `serial` 手填成模拟器的 ADB 地址（MuMu12 常见 `127.0.0.1:16384`）。
