# Codex 05 个人结界突破目标等级模式实施规格

日期：2026-07-31  
适用分支：`codex/mk6657-secondary-development`  
状态：代码首版已实现并通过离线验证；真实游戏动作和识别阈值待 MK6657 分步复核。

## 1. 目标与边界

新增每账号独立的“目标等级模式”，在不删除上游个人结界突破流程的前提下，根据当前九宫格等级与目标等级的关系执行降级、保级或升级。

约束：

1. 新模式默认关闭；关闭后继续使用上游旧流程。
2. 呱太入侵等特殊模式继续走上游逻辑，新模式只负责兼容分流。
3. 上游页面导航、票数 OCR、勋章顺序、进攻、阵容锁定、预设、绿标、御魂切换、胜负结算和奖励处理优先复用。
4. 新模式接管旧 `exit_four`、`three_refresh` 和 `when_attack_fail` 的业务决策，避免两套规则同时生效。
5. 每次刷新后必须重新 OCR 等级，不能假设固定升一级或降一级。

## 2. 已确认规则

### 2.1 棋盘事实

- 当前挑战等级取九格合法等级的众数，不按玩家名字判断。
- 红色“破”表示该目标已成功攻破，不能继续挑战。
- 底部“攻破记录”表示当前棋盘成功人数，可与九格“破”互相校验。
- 3、6、9 胜各可能出现一次奖励弹窗；弹窗在战斗返回棋盘途中出现，点击一次后继续。
- 成功消耗一张突破券；主动投降和正常战败不消耗突破券。
- 同一目标可重复投降；失败箭头只表示该目标至少失败过一次，不显示累计次数。
- 主动投降与正常战败统一计入本轮失败次数。

### 2.2 模式选择

| 条件 | 模式 | 动作 |
|---|---|---|
| 当前等级高于目标 | 降级 | 累计 9 次失败后手动刷新 |
| 当前等级等于目标 | 保级 | 累计 4 次失败，并完成当前棋盘 9/9 成功 |
| 当前等级低于目标 | 升级 | 不主动投降，尽可能完成 9/9 成功 |

### 2.3 降级

1. 读取当前棋盘已有“破”，避免挑战不可用目标。
2. 主动投降或自然战败合计达到 9 次。
3. 条件达到后手动刷新；刷新处于 CD 时保存状态、退出任务，并按剩余 CD 调度回来。
4. 已有“破”只用于恢复成功状态，不减少降级所需的 9 次失败。

### 2.4 保级

1. 有 checkpoint 时，补足到 4 次失败；无 checkpoint 且接管旧棋盘时，不猜测历史重复失败次数，从接管时重新执行 4 次投降。
2. 使用“破”和“攻破记录”恢复当前成功人数。
3. 继续击败所有未破目标，完成 9/9；第九胜由游戏自动刷新，不手点刷新。
4. 如果四次投降之后又发生自然战败，仍完成 9/9，让下一轮等级 OCR 自行纠偏。
5. 自动刷新后重新识别等级，再决定继续保级、降级或升级。

### 2.5 升级

1. 不主动投降，依次挑战未破目标。
2. 9/9 全胜时等待游戏自动刷新。
3. 如果发生自然战败，立即尝试手动刷新；可以刷新则刷新，处于 CD 则保存状态、退出并精确调度。
4. 刷新后重新识别等级，再决定下一轮模式。

### 2.6 结束与恢复

- 有票时继续执行当前模式，不要求剩余票数足够完成整轮。
- 票数为 0，或当前状态无法继续且无法刷新时，退出个人突破并让调度器执行后续任务。
- CD 到期、正常轮到 RealmRaid 或其他任务完成后，再回到棋盘观察并继续。
- 没有 checkpoint 的旧棋盘采用“先执行一次保级尝试，刷新后再按等级纠偏”，不因历史失败次数未知而阻塞。

## 3. 新旧流程分流

```text
进入个人突破
  -> 处理首次弹窗
  -> 检测呱太特殊模式
      -> 是：走上游旧流程
      -> 否：检查目标等级模式开关
          -> 关闭：走上游旧流程
          -> 开启：构建 BoardSnapshot，进入新状态机
```

新模式继续复用：`order_attack`、`general_battle_config`、`switch_soul_config`。  
新模式不使用旧 `exit_four`、`three_refresh`、`when_attack_fail` 作为决策依据。  
`number_attack` 只保留为防失控安全上限，不作为卡级业务完成标准；票数为 0 才是正常票耗终点。

## 4. BoardSnapshot

每次决策前从同一张稳定棋盘截图构建：

```python
BoardSnapshot(
    levels=[...],
    challenge_level=...,
    challenge_level_votes=...,
    broken={...},
    failure_marked={...},
    attack_record=...,
    attackable={...},
    tickets_current=...,
    tickets_total=30,
    refresh_available=...,
    refresh_cd=...,
    confidence=...,
)
```

安全条件：

- 至少识别 6 个合法等级，且等级众数至少 4 票，才允许执行升降级动作。
- `attack_record` 与 `broken` 数量冲突时重试截图；连续冲突则停止本轮动作并留日志。
- 失败箭头只能作为可见下限，精确失败总数来自 checkpoint。
- 自动刷新通过“攻破记录归零、破印清空、棋盘布局变化”组合确认。

## 5. Checkpoint

checkpoint 按账号独立保存，不写进上游任务配置字段，至少记录：

```text
schema_version
account
board_fingerprint
mode
target_level
observed_level
failure_count
success_count
pending_action
pending_refresh
refresh_not_before
last_target
updated_at
```

动作规则：

1. 进攻、投降和刷新前先写 `pending_action`。
2. 动作后重新观察棋盘，以页面证据确认结果，再提交计数。
3. 战斗超过 5 分钟，保存错误截图和 checkpoint 后受控重启；恢复后先对账，不直接增加胜负计数。
4. checkpoint 与棋盘不匹配时不沿用旧计数，进入“无 checkpoint 保级纠偏”策略。

## 9. 首轮实机测试顺序

1. 仅为一个测试账号开启目标等级模式，目标等级设置为当前棋盘等级；其他账号保持关闭。
2. 启动后先看日志中的 `Level board`，人工核对九格等级、`broken`、`failed`、票数和刷新状态；任一不符立即停止并保留 `log/board` 截图。
3. 只观察第一次投降，确认确实返回棋盘、票数不变、checkpoint 的 `failure_count` 增加 1。
4. 继续观察到第 4 次投降，确认没有第五次主动投降，然后只攻击未破目标。
5. 分别观察一次胜利和一次 3/6/9 奖励；确认胜利才扣票、破印和攻破记录一致。
6. 第九胜时确认程序等待游戏自动刷新，没有手点刷新；新棋盘出现后重新 OCR 等级并重新选择模式。
7. 保级链路确认后，再单独测试高于目标的 9 次投降和手动刷新；最后测试刷新 CD 中退出与调度回来。

回退方式：关闭该账号的目标等级模式即可立即恢复旧 RealmRaid 决策，不需要删除 checkpoint；再次开启时程序会先用当前棋盘对账，不匹配的旧 checkpoint 不会直接沿用。

## 10. 2026-07-31 首次实机阻断与修补

11:52 至 11:53 的 `oas1` 实机运行成功通过 Nemu IPC 取得内部 1280x720 画面，并进入个人突破。真实棋盘事实为：前 5 格已有“破”，后 4 格 OCR 均为 58，票数 20/30，刷新按钮可用。原安全门只把 OCR 原始结果 `[0, 0, 0, 0, 0, 58, 58, 58, 58]` 计为 4 个合法等级，低于至少 6 格的要求，因此重试三次后安全退出，并按失败调度到下一次任务时间。该现象不是死循环或绑定失效。

根因是游戏会压暗已破目标的整张卡片，破印下的等级铭牌不再适合沿用未破格 OCR 阈值。离线尝试降低全局阈值只能部分恢复数字，同时会产生 8、56、65、68、88 等误识别，因此禁止用降低全局阈值解决。

修补规则：

1. 先识别破印、失败箭头、原始等级和棋盘签名，不把已破格 OCR 当成可靠等级证据。
2. 首次接管部分棋盘时，所有未破格必须读取到合法等级，并至少有 4 个未破格对同一众数投票，才允许把已破格临时补为该众数。
3. 建立 checkpoint 后，只有当前棋盘签名与 checkpoint 一致，才允许沿用 `observed_level` 补全已破格；这使第 6、7、8 胜后的剩余少量可见目标仍可继续处理。
4. 未破格有任意一个等级读不到时不补全；首次可见等级不一致且众数不足 4 票时不补全；棋盘签名变化时不沿用 checkpoint。
5. 日志同时记录 `raw`、`resolved`、`imputed` 和补全证据来源，不把补全值伪装成 OCR 原始结果。

新增纯逻辑覆盖：5 个已破格不可读而 4 个未破格均为 58 时允许补全；4 个未破格等级不一致时拒绝补全；未破格存在未知值时拒绝补全；第 6 胜后在同棋盘 checkpoint 证据下允许继续。修补后 14/14 用例及 Python 语法检查通过，尚待 `oas1` 对四次投降、剩余四胜和第九胜自动刷新做实机复核。

## 12. 晚间实测前安全化收尾

用户同意按“单事务验证优先”的方式继续。已增加以下约束：

1. `level_mode_config.single_step` 默认开启；每次 RealmRaid 运行最多提交一次投降、挑战或手动刷新，提交后返回庭院并结束本轮任务。
2. 目标等级模式内出现 `GameStuckError` 或 `GameTooManyClickError` 时，保留动作前写入的 pending checkpoint，只结束 RealmRaid，不再转入全局杀游戏重启流程；旧流程的异常策略不变。
3. 开发期 `LEVEL_DEBUG`、`CAPTURE_BOARD`、`CAPTURE_ONLY` 均恢复为关闭；关闭目标等级模式后可正常回退上游旧流程，不再被素材采集开关提前结束。
4. 棋盘签名改为九个对手名字区域的 Otsu 二值化哈希，排除卡片明暗、失败箭头和破印；同一真实棋盘在两张不同时刻截图上签名一致。checkpoint 的棋盘签名改为严格匹配，不允许只凭成功数单调增加沿用旧失败计数。
5. 配置界面明确标注：开启目标等级模式后，旧流程的 `exit_four`、`three_refresh`、`when_attack_fail` 不参与新状态机决策。
6. 12:09 的日志显示第三次投降已完整经过退出确认、失败结算并返回棋盘，但旧函数因使用 ROI 兜底而返回 False，导致 checkpoint 没有提交。晚间实测前将当前 checkpoint 对账为 `failure_count=3`、清除 pending；两次在确认弹窗中触发强制重启的尝试不计入已确认失败。

晚间测试只需启动已停止的 `oas1`。预期本次只再投降一次，使 checkpoint 从 3 变为 4，随后自动返回庭院；不要在同一次运行中继续挑战。确认失败数为 4、票数仍为 20/30 后，下一次单步运行才允许进入一次成功挑战测试。
