## 补充条款 v2.1（2026-08-14 评审后并入，无需重写正文）

### A1（B1 修订）命令端到端幂等（替代 30s/59s 矛盾设计）
- WS 与 REST 共用同一 command_id；Core 增加 CommandLedger（内存，最近 5 分钟 command_id→结果），REST start/stop 接受可选 command_id 查询参数并先查账本回放。
- Bridge 时序：发 WS → 等 ack（T_ack=2s）→ 已 ack 等回执（T_exec=30s）→ 超时返回 HTTP 202 {status: in_progress, command_id}（**不报失败**），结果经查询端点 GET /api/v1/commands/{command_id} 或事件通道补取；未 ack 才 REST 兜底（带同一 command_id）。
- 测试覆盖：①ack 丢失但命令已执行（REST 回放不重复执行）；②59s 迟到回执经查询/事件通道可得；③202 语义。验收证据含 Core 侧账本命中日志。

### A2（B2 修订）服务端 owner 裁决
- 服务端 owner_id 恒为唯一 tabId；browser_instance_id 仅作前端同浏览器分组，绝不上报为 owner。
- leader 选举优先 Web Locks API（原子），BroadcastChannel 仅通知；无 Web Locks 时允许双 leader，但服务端租约是最终裁决——同一 session 同时只有一个 tabId 持活租约（fencing + 同 owner 活租约逻辑保证）。

### A3（B3 修订）活跃客户端集合
- 服务端保存 {tabId: {build, last_seen_at}} 集合（按 last_seen 剪枝）；验收 = 窗口内无「活跃旧版本」，不用单一 last_seen_client_build。

### A4（B5 修订）真实并发
- 验收用两个线程/进程 + barrier 同步发起；分别覆盖 Xiuxing 与普通任务；断言恰一个成功、一个 409、最终值=成功者。

### A5（R-1 修订）测试模式无操作 worker
- worker 经测试模式注入：harness 在临时 cwd（含临时 config/ 与 ds14nop 账号，**绝不落生产 config/**）经 ScriptProcess 启动；worker 实际经过 Script.__init__ 的 logger.hr('Start',0)→rule→print→FlutterLogStream 路径。
- 场景 A：父进程被杀（模拟旧强杀）→ 孤儿 worker 下一次写日志降级不崩（覆盖管道修复）；场景 B：优雅停止 → worker 随停无孤儿；场景 C：start.ps1 -RestartCore 全栈 5 轮（补充性，生产 oas1 不参与）。每轮保存父子 PID 快照。

## 阻断项修订

### B1（原 O14-1）双发：改用 command_ack 判定接单状态
- 修复：Bridge 记录 ack——command() 发送前登记 command_id，收到 command_ack 时置 self._command_acks[command_id]=True（并在 60s reap 同步清理）；command() 超时分支改为：ack=True → 不触发 REST 兜底，继续等待回执至执行窗口（30s，shield 保住 future），超时仍未回执则抛「执行中未回执」错误并保留宽限期；ack=False → 允许 REST 兜底（Core 未接单）。main.py _send_account_command 相应分支化。Core 侧无需改动（ack 已存在）。
- 复现条件：FakeWebSocket 可配置 ack 与回执的到达时序（ack@0.1s+result@2.1s；ack@0.1s+result@59s；无 ack；ack 无 result）。
- 行为测试：四种时序各断言「是否二次下发」——ack 到达则 0 次 REST、无 ack 才 1 次；59s 迟到回执被采纳。
- 运行态验收：真 Core 上以 timeout=0.05 触发（start 已运行→Core 幂等拒绝为辅助观察），server.txt 中无重复 start 记录。

### B2（原 O14-9）owner 模型：标签级 tabId + 浏览器实例 ID + 领导选举
