## ② 新发现问题清单

**N1 🔴 `mark_artifact_damaged` 写入非法 state，删除受损工件路径必然抛 `IntegrityError`，并使 reconcile 中断且文件库/DB 状态分裂**（置信度=已证实）
- 现象：`repository.py:3057-3064` `mark_artifact_damaged` 执行 `UPDATE artifacts SET state='damaged' …`，但 schema CHECK 约束仅允许 `('staging','ready','delete_pending')`（`repository.py:570`）。
- 证据：我用标准库 `sqlite3 :memory:` 按 `_schema_statements` 同款建表后执行该 UPDATE，**100% 抛出 `sqlite3.IntegrityError: CHECK constraint failed: state IN (...)`**（仅内存复现，未触碰项目数据）。
- 影响：`runtime.py:1959-1982` 在 `reconcile_artifacts(apply_repairs=True, quarantine=True)` 下——正是 `maintenance.py:178` `quarantine` 命令的运行路径——先把文件 `quarantine_file` 移入 quarantine、再把 `quarantine_items` 置 `quarantined`，随后 `mark_artifact_damaged` 抛错：
  - reconcile 首个受损工件即异常中断（异常无捕获，向上冒到 maintenance.to_json）；
  - 文件已被移走，但 `artifacts` 行仍是 `state='ready'` 且指向已不存在的路径 → 文件系统与 DB 状态不一致；
  - 后续所有受损工件不再处理。
- 注：`tests/test_full_remediation.py:320-330` 只测 `reconcile_artifacts()`（`apply_repairs=False`）的报告值，未覆盖 repairs 路径，故套件未捕获。且 `damaged` 亦不在 `_validate_schema` 的 `required_sql_fragments["artifacts"]`（`repository.py:786`）中，进一步印证枚举不合法。
- 建议方向（供后续，本轮不改）：要么给 artifacts 表增加 `damaged` 枚举并同步 `_validate_schema`，要么 `mark_artifact_damaged` 改为 `state='delete_pending'`/直接删行；并让 reconcile 对单工件异常继续处理后续项。

**N2 🟡 quarantine 目录完全无配额、无过期、无 GC**（置信度=已证实，即历史项 #4 的独立复述）
- `artifacts.py:245-284` `plan_quarantine`/`quarantine_file` 把文件移入 `root/quarantine/<YYYYMMDD>/…`；`permanently_delete_canvases`（`runtime.py:541-593`）与 `reconcile_artifacts` 的 orphan 分支（`runtime.py:2072-2089`）持续写入。无字节/文件数上限（`ArtifactStore.usage()` 虽 os.walk 到 quarantine，但配额守卫只基于 DB artifacts 表 staging/ready 行），长期永久删除累积磁盘无回收路径。

**N3 🟡 file-move 与 DB 标记不同顺序导致的收敛缺陷**（置信度=已证实，N1 的衍生）
- `reconcile_artifacts` 对受损工件先 `quarantine_file`（文件系统，不可回滚）再 `mark_artifact_damaged`（DB）；一旦后者失败即留下"文件已移走、DB 仍 ready"的中间态。对比 `permanently_delete_canvases` 正确的补偿模式（`runtime.py:575-593` catch 后 `restore_quarantine` 回滚）——reconcile 缺同样的补偿。

**N4 🟡 annotation 配额计数 total（含软删除）vs 文档 "active" 措辞**（置信度=已证实）
- `runtime.py:2675` `if len(session.annotations) >= self.max_annotations` 计数的是 session 内存 dict 全量条目；软删除只 `replace(current, …, deleted_at=_now())` 保留在 dict（`runtime.py:2823`），因此历史删除累积可永久耗尽 "200 个活动标注" 的配额。文档口径与计数语义不符（延续 audit B4，仍未修）。

**N5 🟢 SQL 注入——未发现**（置信度=已证实，归入通过项）
- `repository.py` 全部写读均为 `?` 占位符参数化；唯一 f-string 用于 `IN ({placeholders})` 的占位符个数（`placeholders=",".join("?" for _ in unique_ids)`，不含任何用户值，见 `repository.py:2140,2175,2228,2816`）；`list_canvas_summaries` 的 LIKE 搜索做了 `\ % _` 转义（`repository.py:1986-1988`）。PRAGMA/表名均为固定字符串。

**N6 🟡 bundle 画布**「8192×8192」无像素积上限，comparison 可超量分配**（置信度=已证实）
- `bundles.py:275-276` `_canvas_spec` 只查 `width/height ≤ 8192`，**不查 `width*height`**；对比单帧截图有 `MAX_FRAME_PIXELS=32_000_000` 上限（`common.py:30,39`）。`comparison.py:24-30` `_canonical_rgb` 会把任意 payload `resize` 到 `(canvas.width, canvas.height)`——8192×8192≈67M 像素，`ImageChops.difference`+`split`+`lighter` 复数副本峰值内存数百 MB。`compare_backgrounds`（`runtime.py:2587-2630`）消费的正是 session.canvas 尺寸。这正是 CC-BUNDLE-001 曾担心的 "later comparison can allocate" 的残余桩——只限了单边没限乘积。

**N7 🟢/🟡 路径安全基本成立，附 Windows 保留名注意事项**（置信度=高概率）
- `artifacts.py safe_path/safe_root_path`（58-91）做 `is_absolute`/`..`/`.` 拒绝 + `_validate_component` 正则 `[A-Za-z0-9_.-]+` + 逐级 `_reject_reparse`（拒绝 symlink/junction，`st_file_attributes & 0x400`）。我用 stdlib 实测 `D:data`、`a:b`、`C:Program Files` 这类盘符相对路径会被 `abspath` 展开后 `relative_to(base)` 拒绝或吞到 root 内子路径，不逃逸出 data 根。但 `con.png`/`nul` 等 Windows 保留设备名可被 `safe_path` 接受（`safe_path` 不校验保留名）——写入阶段 `open("xb")` 会抛 OSError 而非写坏，风险低。HTTP 层 session_id/annotation_id 均有正则/uuid 约束，不能直接注入任意 relative_name。

**N8 🟢 文件原子写/fsync 实现良好**（置信度=已证实，归入通过项）
- `save_bytes`/`save_bounded`：tmp + `flush` + `os.fsync` + `os.replace`（`artifacts.py:98-109,179-190`）；`promote_staged` 先校验 SHA-256 再 `os.replace`（116-137）；`quarantine_file`/`restore_quarantine` 均先 hash 校验再 `os.replace`。单进程内 `ArtifactStore._lock` RLock 串行化。

**N9 🟡 nemu 超时线程残留（低风险）**（置信度=高概率）
- `nemu_ipc.py:309-341` 超时后 `future.cancel()` 不终止 executor 线程；该线程最多存活至底层 socket timeout（`nemu_ipc.py:95` `settimeout(self.timeout_seconds)`，超时在 `_receive_packet` 触发 `terminate()` 并抛错），故不会永久卡死，但存在 `timeout_seconds` 量级的死线程。`close()` 用 `shutdown(wait=False)`（372）不等待。连接不重用：每次 `from_descriptor` 重新 spawn 子进程 + 新 socket。设计符合 audit 建议方向，遗留线程为已知残余。
