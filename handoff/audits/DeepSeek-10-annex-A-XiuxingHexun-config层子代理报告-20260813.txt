## ② 边界问题清单（按严重度）

### 🟡-1 | 主循环无计数上限时，唯一终态完全依赖 OCR 票务耗尽判定
- **证据**：`script_task.py:87` `while max_challenges == 0 or completed < max_challenges:`；`config.py:25-31` 默认 `max_challenges=0`（"continue until activity reports no tickets"）。
- **根因**：`max_challenges==0` 使循环退化为无上限；唯一正常出口是 `_search` 返回 `EMPTY`（`script_task.py:89-90`），而 EMPTY 依赖 `I_SEARCH_AVAILABLE` 模板失配 + 稳定零票 OCR。若活动皮肤/分辨率导致搜索按钮模板仍匹配（代码注释 `:426-434` 反复讨论该场景），任务只能靠 OCR 零票确认兜底，任何 OCR 把非零读成零的抖动都被 3 采样拦截，反之把 0 读成非 0 且搜索按钮仍匹配则可能空转。
- **置信度**：待实机（每轮子步骤均有 deadline + 失败即 raise，**不构成「break 落进尾部无条件 raise」类的 P1 回归**，该历史模式在 743 行内逐 break 排查未发现：`break` 仅出现在 `:376/380/654/658`，均无尾坠 raise）。
- **最小修复**：建议对「搜索无结果且非零不稳定」路径增加连续空转上限计数，或文档明示 `max_challenges` 应为活动限期内保守值。

### 🟡-2 | `_recover_existing_result` 单凭 VICTORY 标题模板即记 VICTORY
- **证据**：`script_task.py:132-142`；模板文件 `res/battle_result_victory_title.png`（`assets.py:111`）。
- **根因**：只要 `I_RESULT`（victory_title 模板，threshold 0.8）匹配就 `record_battle_result(VICTORY, recovered=True)`。若重启时结算页实际是战败，模板应不匹配（标题不同），会落空并继续走安全 `_fail`；但若战败页局部与胜利标题相似度 ≥0.8，则可能误记胜利并 `completed+=1`。
- **置信度**：待实机（模板为胜利专用标题，误匹概率低——实测该模板均值 75、非黑底，见⑤）。
- **最小修复**：可增加 DEFEAT 标题负模板互斥校验后再生效 recovered VICTORY。

### 🟡-3 | `Config.schedule()` 存在 __setattr__ 自动保存与显式 save 重复触发
- **证据**：`module/config/config_model.py:191-199`（`__setattr__` → `self.save()`，已加 `key.startswith("_")` 短路保护）；`module/config/config.py:212-254` `schedule()` 中 `scheduler.next_run = when`（触发自动 save）后再 `self.save()`。
- **根因**：这是历史上 write amplification 的延续。实际效果：`schedule()` 内 `reload()` 重建 model（baseline=最新磁盘态），赋值触发一次 merge 写入，随后显式 `save()` 因 baseline==current 走 `merge_changed_json` 早退（`config_transaction.py:156-157` 无更新直接 return），**二次调用是冗余读+无操作，并非双重原子写**。但任何对 model 连续多字段赋值仍会产生 N 次 save。
- **置信度**：高概率（读代码可证早退逻辑）。
- **最小修复**：在 `save()` 内或 `schedule()` 内聚合单次 merge 提交，避免依赖 __setattr__ 隐式保存的副作用语义。

### 🟡-4 | 批量 PATCH 路由有 revision 门禁，旧单值 PUT 路由（非 XiuxingHexun 分支）无 revision 门禁
- **证据**：`script_router.py` `script_set_values`（PATCH）强制 `expected_revision`（428/409）；`script_set_value`（PUT，`:393-397` 非 xiuxing_hexun 分支）仍走 `mm.config_cache(...).model.script_set_arg` → 仅靠 `ConfigModel.save()` 的 merge（无 HTTP 层 428/409）。
- **根因**：两条写入口的并发/校验语义不对称；旧路由写同一字段时靠 3-way merge 兜底，但对调用方不报冲突。
- **置信度**：已证实（diff 可读）。
- **最小修复**：让 PUT 单值路由也复用 `apply_json_patch` + revision 检查，或明确旧路由为兼容遗留。

### 🟡-5 | 服务器测试与真实 Core 共享账号租约文件，测试环境会互相污染
- **证据**：`module/server/tests/test_script_process.py:64-95` `ScriptProcessLifecycleTest` 不 mock `AccountRunLease`，直接 `ScriptProcess('oas1')`；租约路径派生自 `Path.cwd().resolve()::oas1`（`script_process.py:47-49`），落到真实 `Temp/oas-account-leases/b0952a...lock`。实跑发现该锁被一个仍在运行的 python.exe（PID 5936 等）持有（`PermissionError: [Errno 13]`），9 个生命周期用例全部 `AccountLeaseError: account lease held by another Core: oas1`。
