# CommonPopup 通用弹窗门卫

`CommonPopup` 只处理会覆盖任意业务页面、且已经有可靠业务语义证据的全局阻断弹窗。它不是通用“确认按钮点击器”，战斗结算、准备页、购买、奖励、RealmRaid 攻击确认和页面导航不应注册到这里。

## 运行链路

`BaseTask.screenshot()` 和百鬼快速截图都进入同一个受保护截图入口：

```text
设备原始截图
-> CommonPopupDispatcher 按优先级检测
-> 最多处理一个命中项
-> 获取同设备、同尺寸、递增 frame_id 的新帧
-> 从最高优先级重新扫描
-> 连续两张有效帧不再出现目标实例
-> 把最终稳定帧交给业务逻辑
```

当前处理器：

| popup_id | 优先级 | 行为 |
|---|---:|---|
| `long_idle_buff_prompt` | 900 | 廉价像素预筛、OCR 语义确认、安全区域内随机点击 |
| `friend_invitation` | 800 | 每张新帧重新识别邀请类型并按账号策略接受、拒绝或忽略 |

优先级 `1000` 保留给未来经过真实证据验证的网络或会话阻断。普通确认按钮模板不能单独授权点击。

## 分发边界

- 总预算为 6 秒、6 轮、4 次动作；同一弹窗实例最多动作两次。
- 处理器只能实现 `detect(context)`、`act(context, detection, attempt)`，以及可选的 `on_resolved`、`on_abort` 回调。
- 处理器不得截图、循环、导航页面、调用其他处理器或调用 `BaseTask.screenshot()`。
- 全局 6 秒预算在首张截图之前建立；同一个绝对 deadline 传入后续截图、OCR、检测和动作。
- 捕获源或 OCR 后端不能提供 deadline 保护时，允许检测和记录，但不得执行 `enforce` 自动点击。
- “15 分钟未使用加成”同一实例最多点击一次；点击后等待关闭动画，并以连续两帧消失作为解决证据。
- 好友邀请实例由策略、奖励类型、可用邀请身份和稳定内容指纹共同区分；同类型新邀请必须重新计算策略。
- 分发器统一负责截图刷新、优先级、重试、连续消失验证和总预算。
- 黑帧、错误尺寸、设备身份变化、未递增 `frame_id`、动作异常和回调异常均 fail-closed，抛出结构化 `GameStuckError`。
- `PopupVerification` 是公开数据契约的预留模型；当前 v1 使用分发器共享的“重新检测加连续两帧消失”验证器，不允许处理器各自实现截图验证循环。

## 长时间加成模式

配置项 `global_game.emergency.long_idle_buff_prompt_mode`：

- `disabled`：不检测、不 OCR、不点击。
- `detect_block`：识别到目标弹窗后安全停止，不点击。
- `enforce`：识别后在 `[705,778) x [411,434)` 内随机确认，并验证连续两帧消失。

默认值暂为 `enforce`，用于兼容现有运行配置。真实灰度时可先改为 `detect_block`；模式调整属于用户配置操作，不由代码迁移自动改写。

## 证据

普通无弹窗帧不写文件。首次命中后，证据写入：

```text
log/evidence/common_popup/YYYYMMDD/<event_id>/
```

目录包含点击前帧、每次动作后的新帧、第二张稳定帧和 `manifest.json`。清单记录账号、任务、设备身份、截图方式、帧 ID、像素与文件 SHA-256、OCR 证据、点击点、动作次数、耗时和最终状态。证据写入异常会写日志，但不会授权额外点击。

## 新处理器准入

新增处理器前必须具备：

1. 明确的跨页面业务语义，不能只依赖按钮外观。
2. 正样本和足量相似负样本，历史负样本误点击为零。
3. 单帧 `detect()`，不得在处理器内部等待或截图。
4. 明确优先级、实例键、安全动作区域和最多动作次数。
5. 组合弹窗、动作丢失、连续两帧消失、黑帧、错设备和预算耗尽测试。

生产任务中的原始 `device.screenshot()` 只允许出现在 `CommonPopupDispatcher`。静态测试会拒绝其他业务旁路。
